# 评审维度与权重

| 维度 | 权重 | 关注点 |
|---|---|---|
| 正确性 | 0.30 | 数学推导是否有错、代码逻辑与公式是否一致、量纲是否统一 |
| 完整性 | 0.20 | 是否回答了全部小问、必备要素是否齐全 |
| 可复现性 | 0.20 | 参数是否给全、随机种子是否固定、别人能否照着跑出同样结果 |
| 规范性 | 0.15 | 结构、术语、图表引用、格式是否符合竞赛要求 |
| 创新性 | 0.15 | 是否有超出常规套路的思考 |

# 评分红线（触发即在该维度扣至低分，并列入 must_fix）

**本环节适用的数值规则**：{{ number_policy }}

1. **数值违规**：违反上面这条数值规则 → 正确性扣至 4 分以下。
2. **编造文献或数据**：参考文献、实验数据被凭空生成 → 正确性扣至 3 分以下。
3. **公式与实现不一致**：建模写的公式和代码实现的不是一回事 → 正确性扣至 5 分以下。
4. **有未解决的问**：任何一个小问没有对应结论 → 完整性扣至 5 分以下。
5. **不可复现**：缺参数、缺种子、路径写死 → 可复现性扣至 6 分以下。
6. **空话充数**：大段无信息量的套话、占位符未替换 → 规范性扣至 6 分以下。

# 输出格式（**只输出 JSON**，不要解释性文字，不要 Markdown 代码块围栏）

{
  "stage": "{{ stage_id }}",
  "scores": {"正确性": 0, "完整性": 0, "可复现性": 0, "规范性": 0, "创新性": 0},
  "total": 0.0,
  "verdict": "pass 或 revise",
  "previous_check": [{"item": "上一轮必改项原文", "status": "已落实|部分落实|未落实", "evidence": "依据"}],
  "strong_points": ["值得保留的做法"],
  "issues": [
    {"severity": "高|中|低", "location": "章节/文件/行号", "problem": "具体问题", "fix": "具体改法"}
  ],
  "must_fix": ["必须修改项，按优先级排序，每条都要能让作者直接动手改"],
  "next_focus": "如果只能再改一处，改哪里最值"
}

规则：
- `total` = 各维度按权重加权后的分数，保留一位小数，范围 0-10。
- `verdict` 仅当 `total >= {{ pass_score }}` 且没有"高"严重度问题时才是 `pass`。
- `must_fix` 不超过 8 条，每条必须是**可执行动作**，不要写"建议进一步优化"这类空话。
- 如果产出确实扎实，如实给高分，不要为凑问题而编造问题；但一旦命中评分红线，必须严格执行。
- **再次强调：你的整个回复必须是一个合法 JSON 对象**，以便程序直接解析。
