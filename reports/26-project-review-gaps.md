## 1. ★ 最严重：导出会**覆盖 agent 写的论文**

### 证据
对一个真实跑完的工作区调 `POST /api/paper/export`：

```
sections   0
figures    0
references 0
tables     0
body_chars 0
notes: ['未找到正文（paper/sections/*.md 或 paper/main.md）']
pages      2
```

同一工作区的 `paper/` 目录：`main.tex` **1,845 B**（只有标题 + 2 张表）。
而 agent 在 `comp-paper-zh` 步骤里写出的是 **27,538 B** 的完整论文。

### 根因（两层）

1. **格式错配**：引擎的 `build_paper` 只认 `paper/sections/*.md` 或 `paper/main.md`
   （Markdown 分节），而 agent **直接写 `paper/main.tex`**（成品 LaTeX）。
   两边对"论文产物是什么格式"没有约定，也不互相检查。

2. **覆盖而非保护**：`export_latex` 以 `paper/main.tex` 为默认输出名，
   **无条件覆盖**。agent 的成品就此丢失，且**没有任何告警**——
   导出还报 `ok: true`。

### 后果
- 一次导出即可摧毁 `comp-paper-zh` 的全部产出
- 引擎会产出"看起来成功、实际是桩"的 2 页 PDF（**又一次** `size > 0` 式假成功）
- 这与第 7.2 节的缺陷 10（编译失败被误报成功）是**同一类问题的复发**

### 待办
1. 导出前**检测已存在的 `paper/main.tex`**，若是 agent 产物则改名保留（如 `main.agent.tex`）
2. 明确两种路径：**Markdown 分节 → 引擎生成** vs **agent 直出 .tex → 引擎只编译**
3. 在报告里**显式区分** `body_chars=0` 的"空正文导出"与正常导出

## 4. 运维与健壮性缺口

### 4.1 僵尸工作流无清理机制
- 数据库里长期滞留 **2 个 `running`** + 11 个 `failed` 工作流
- 上一轮排查中，**9 个僵尸 `running` 同时存在**，与真实运行争抢 agent 进程，
  导致我一度误判"审计没触发"
- 有 `/repair` 端点，但**没有自动调用**（仅手动）

**待办**：服务启动时自动 `repair_orphans()`；或加定期心跳回收。

### 4.2 单步等待上限需按实测调整
- 脚本默认单步上限 25 分钟，而 `comp-paper-zh` 实测 **24.5 分钟**——边界太紧，
  一次运行就因此中断
- 建议按步骤区分上限（写作类给 40 分钟，分析类给 15 分钟）

### 4.3 论文导出曾报 500（未能复现）
上一轮 `POST /api/paper/export` 返回 **HTTP 500**，本轮重试变 200。
**未定位**——可能是工作区状态相关的偶发。日志已丢失。

### 4.4 无日志归集
服务以 background job 运行，**日志随 wrapper 退出而丢失**。
排查时多次受影响（如 `log.info` 没配 handler 导致看不到自己的日志）。

### ★ 第 25 项的方法学意义

**校验器自己也会有 bug，而且它的 bug 会让后续所有检查失真。**

第 23 项（前向引用 `??`）在第一次运行里**明明存在**，而版面校验器报「无未解析交叉引用」——
因为它查的是 `???` 而实际占位是 `??`。
修好这条正则之后，校验器**立刻**抓出了第 23 项。

**结论：校验链上任何一环失效，下游全部假绿。** 所以校验器本身也要有测试
（`test_layout_verifier_catches_double_question` 就是喂一份故意坏的 PDF 给它，断言它必须报错）。
