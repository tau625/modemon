# 缩小与蓝方差距：执行计划

> 依据：`27-alignment-assessment.md`（对齐度）+ `26-project-review-gaps.md`（缺口）
> 原则：**先修正确性、再补覆盖面、最后做打磨**；每项都给出验证方式。

---

## 0. 一个决定优先级的结构性发现

蓝方的 **30 个模板并不等于 30 套流水线**：

| 编排 | 覆盖模板 | 数量 |
|---|---|---|
| 中文六阶段（`赛题分析 → 建模 → 编程 → 图表 → 论文 → 编译`） | 18 个中文竞赛（含天府杯/认证杯/MathorCup/五一杯…） | 18 |
| 英文六阶段（`Analysis → Modeling → Code → Figures → Paper → Compile`） | 4 个英文竞赛（美赛/数维杯国际/亚太/小美赛） | 4 |
| **统计建模专用**（`选题规划 → 数据采集分析 → 图表 → 论文 → 编译`） | `comp_stats` | 1 |
| 学术写作族 | 5 个 + `paper_writing` 内部分支 | 6 |
| 软著/专利 | `ip` 族 | 2 |

**结论**：补 22 个竞赛模板**主要是补注册表数据**（名字/赛期/语言/页数/星级/分组），
不是写 22 套 DAG。真正要写代码的只有 **`comp_stats` 那套 5 步编排**。

这把"模板 30% → 73%"这件事从"人月级"降到"**天级**"。

## 阶段 0：P0 正确性修复（必须先做）

### 0.1 导出不得覆盖 agent 产物
| 项 | 内容 |
|---|---|
| **问题** | `export_latex` 默认输出 `paper/main.tex`，**无条件覆盖**。实测 agent 写的 27.5 KB 论文被覆盖成 1.8 KB 桩 |
| **改哪** | `services/latex_export.py::export_latex` |
| **怎么改** | ① 输出前检查已存在的 `main.tex`，若**非本次生成**则改名为 `main.agent.tex` 并保留；② 用"生成标记注释"判断归属 |
| **验证** | 新测试：预置一个 agent 版 `main.tex` → 导出 → 断言原文件仍在、新文件另名 |
| **量级** | ★ 半天 |

### 0.2 显式区分"空正文导出"
| 项 | 内容 |
|---|---|
| **问题** | `body_chars=0` 时仍报 `ok: true`，产出 2 页桩 PDF |
| **改哪** | `export_latex` 的 `ok` 判定 |
| **怎么改** | `body_chars == 0` → `ok: false` + 明确 `error`，或至少 `degraded` 标记 |
| **验证** | 新测试：空工作区导出 → 断言 `ok is False` |
| **量级** | ★ 1 小时 |

### 0.3 引擎/agent 论文格式约定
| 项 | 内容 |
|---|---|
| **问题** | 引擎只认 `paper/sections/*.md`，agent 直写 `paper/main.tex`，两边无约定 |
| **改哪** | `services/paper_build.py::build_paper` + 步骤提示 |
| **怎么改** | ① 支持"已有成品 .tex"路径（只编译不重建）；② 在 `comp-paper-zh` 提示里**明确要求**写 `paper/sections/*.md`，由引擎装配 |
| **验证** | 端到端：跑 `comp-paper-zh` → 断言产出 `paper/sections/` 而非直出 `.tex` |
| **量级** | ★ 1 天（含提示词调优） |

## 阶段 1：补齐模板面（性价比最高）

### 1.1 模板注册表（22 个竞赛 + 5 学术 + 2 软著/专利）
| 项 | 内容 |
|---|---|
| **数据来源** | `04-methodology.md` §3.2 已有**完整 22 行表格**（value/label/赛期/lang/pages/stars） |
| **改哪** | 新增 `services/template_registry.py`；`workflow_engine.resolve_template` 改为查注册表 |
| **怎么改** | 注册表项：`value / label / month / lang / pages / stars / group / sequence` |
| **⚠️ 附带修一个缺陷** | 实测 `resolve_template("comp_tianfu")` **抛 `TypeError`**——`TemplateType` 是枚举，未知值直接失败。注册表化之后应改为**优雅回退**到通用中文序列并记 `degraded`，而不是崩 |
| **验证** | ① 断言 30 个 value 全部可解析；② 断言未知 value **不抛异常**且被标记降级 |
| **量级** | ★★ **1–2 天**（纯数据录入 + 接线） |

### 1.2 `comp_stats` 专用编排（唯一需要新代码的序列）
| 项 | 内容 |
|---|---|
| **编排** | `选题规划 → 数据采集分析 → 图表 → 论文 → 编译`（5 步，**与六阶段不同**） |
| **改哪** | `workflow_engine.py` 加 `comp_stats_steps()`；`resolve_template` 分支 |
| **怎么改** | 步骤名可从蓝方 `desc` 反推：`comp-topic-plan` / `comp-data-analysis` / `paper-figure` / `comp-paper-zh` / `comp-compile-zh` |
| **验证** | 新测试：`comp_stats` 返回 5 步且首步是选题规划 |
| **量级** | ★ 半天 |

### 1.3 华为杯机制（蓝方称为"deliberate exception"）
| 项 | 内容 |
|---|---|
| **蓝方原文** | 「has its own graduate-level mechanism and solver-depth Skill, so callers can select it without duplicating the DAG」 |
| **要点** | ① 研究生级机制；② **求解深度 skill**；③ 通过**步骤级 select** 实现，不复制 DAG；④ 签名模板包 `comp-paper-zh/templates/huawei`，缺失时 **fail-closed**（宁可失败不降级 `ctexart`） |
| **改哪** | 步骤级 `select` 支持；`comp_huawei` 映射到"zh 序列 + huawei 变体" |
| **验证** | 新测试：`comp_huawei` 复用 zh 序列长度但带 huawei 标记；缺模板时不降级 |
| **量级** | ★★ 1–2 天（需要设计"变体"抽象） |

## 阶段 3：运维健壮性

### 3.1 僵尸工作流自动清理
| 项 | 内容 |
|---|---|
| **问题** | DB 长期滞留 `running` 僵尸；实测一次排查中**9 个并发**争抢 agent 进程 |
| **改哪** | `main.py` 启动钩子 |
| **怎么改** | `@app.on_event("startup")` 调 `repair_orphans()`；另加定期心跳（如每 5 分钟）回收超时 `running` |
| **验证** | 新测试：造一个僵尸 `running` → 调 startup 钩子 → 断言变 `failed` |
| **量级** | ★ 半天 |

### 3.2 单步上限按步骤分级
| 项 | 内容 |
|---|---|
| **问题** | 脚本默认 25 分钟，而 `comp-paper-zh` 实测 24.5 分钟——边界太紧 |
| **怎么改** | 按蓝方 `_step_inactivity_timeout` 的分级：写作类 40 分钟，分析类 15 分钟 |
| **量级** | ★ 1 小时 |

### 3.3 日志归集
**问题**：服务以 background job 运行，日志随 wrapper 退出丢失；`log.info` 没配 handler。
**改法**：加 `logging.FileHandler` 写到 `backend/logs/modemon.log`，按天轮转。
**量级**：★ 1 小时

### 3.4 追查论文导出偶发 500
**现状**：上一轮报 500，本轮复现为 200，**未定位**。
**改法**：给 `/api/paper/export` 加异常兜底日志（记录 workspace 状态 + traceback）。
**量级**：★ 半天（取决于能否复现）

| 次序 | 项目 | 量级 | 收益 |

| — | 前端多页面 / 账号计费 | 1–2 周 / — | **暂缓 / 不做** |

- 模板 30% → 100%（名字级）/ 编排 67% → 100%
- 核心 API 面 17% → ~25%
- 竞赛主线 80% → ~95%
- 并消除唯一的 P0 数据丢失风险
